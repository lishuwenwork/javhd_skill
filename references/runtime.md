# 运行协议

本文件面向负责执行本 skill 的 agent。所有相对路径以 skill 根目录为基准，不依赖 agent 的当前工作目录。

## 入口与参数

使用本 skill 的虚拟环境解释器运行 `scripts/main.py`，始终带 `-I`。脚本会且只会把自己的 `scripts` 目录加入模块搜索路径。

| 参数 | 行为 |
| --- | --- |
| `--init-db` | 通过 Cloudflare D1 REST API 初始化记录表，不上传 |
| `--check` | 本地自检；不登录、不下载、不发布 |
| `--login all` | 同时初始化/复用两侧登录 |
| `--input "电报重登"` | 重新登录 Telegram |
| `--input "夸克重登"` | 重新登录夸克 |
| `--id 123 --tags "#4k、#高清"` | 执行一个视频任务 |
| `--ids 123 456 789 --tags "#4k"` | 按输入顺序批量处理，共用标签；`--id` 也支持多个值 |
| `--id 123 --url "<详情页URL>"` | 从指定详情页解析完整源，不拼接 ID 地址 |
| `--input "id:123 标签:#4k、#高清"` | 接收原始指令；优先使用上面的独立参数形式 |
| 多行 `--input` | 每行一个 `ID：… URL：… 标签：…`；URL、标签可省略，明确每个 URL 属于哪个 ID |
| `--retry "<TASK_DIR>"` | 用户选择后复用保留媒体，只重试未成功平台；不得自动调用 |
| `--delete "<TASK_DIR>"` | 用户选择后仅删除指定保留任务目录，不登录；不得自动调用 |

不要同时启动多个命令；同一安装目录的运行锁覆盖登录、单条和整批视频任务。自检不获取锁，不启动任务。先验证整批输入，再读取配置；字段名 ID/URL 大小写均可，支持中英文冒号。ID 列表用逗号、顿号或空白分隔；同批重复 ID 合并标签及非冲突 URL，保持首次位置；同一 ID 的 URL 冲突或一组多个 ID 只有一个 URL 时拒绝，不猜对应关系。

## 批量调度和详情页

一个生产者串行执行“创建任务 → 解析详情页/生成完整链接 → 下载及准备媒体”，一个消费者串行执行视频上传生命周期。生产者必须等当前视频准备完成，才开始下一条解析；消费者必须等当前视频两端上传及收尾结束，才开始下一条。两阶段可交叠，同一视频电报和夸克仍通过原 `settle` 并发。媒体容量为二，最多一个正在上传、一个下载中或待上传；等待容量前不解析后续链接。

用户提供详情页 URL 时，`resolve`、`prepare_media` 和诊断 `probe_video.py --url` 直接用该地址；只允许 JAVHD 主站/子域的无凭据 HTTP(S) URL，保留路径和查询参数，页面内部 ID 和播放器路由仍从该页取得。请求失败不会回退到 `/zh/id/{id}`；仅未指定 URL 时使用默认路由。任务清单保存用户详情页 URL 以便预处理失败后重新解析，不保存临时视频链接。旧任务缺少 `page_url` 时按原默认行为处理。

每项单独收尾、写入 D1 上传记录并输出结果事件；一项失败保留其媒体并继续后续项，等待用户决定失败项的重试或删除。批次中止停止生产者，不开始下一条上传，等待已在上传的视频结束；已准备或正在准备的未上传任务转为保留，未轮到下载的 ID 标为跳过。不自动恢复批次或重传失败项；首次批量交接不属于 `--retry`，夸克首次上传仍创建自己的新断点。

## 配置

ACCOUNT_ID、DATABASE_ID、API_TOKEN 是 D1 API 连接配置；首次初始化和失败补写规则见 [D1 说明](d1.md)。不再生成上传历史或单条/批次结果 JSON，结果由本次进程事件和 D1 提供，本地只保留运行和失败恢复状态。

根目录的本地 `config.json` 是唯一运行配置文件；分发包仅携带空白的 `config.example.json`，不包含个人配置。首次安装仅在 `config.json` 不存在时复制模板，再在本地填写真实配置；升级时保留已有配置，不用模板覆盖。程序不会自动创建配置，也不直接读取模板；缺少本地配置时会提示复制模板。所有路径都从 skill 的实际位置计算。个人配置、登录会话、二维码和 Cookie 文件不打包；自己的 `config.json` 可单独私下迁移，迁移前先核对目标机器已有配置。

- `telegram_channel_id`：唯一的频道目标配置来源。`0` 表示尚未设置；上传前必须是 `-100` 开头的频道 ID，数字或数字字符串均可。
- `telegram_premium`：JSON 布尔值，默认 `false`，旧配置缺失时也按 `false` 处理。`false` 的普通账号使用约 2GB 上限并自动分段；`true` 的会员不切割，使用约 4GB 上限上传原视频，超过后失败而不是自动切割。必须与实际账号会员状态一致，不从环境变量覆盖。
- `telegram_split_direction`：`tail` 或 `head`，默认、分发模板及旧配置缺省均为 `tail`，只从本地配置读取。`tail` 从总字节数向前选择关键帧，余量留在首段；显式设置 `head` 则正向规划，余量留在末段。切点输出和文件编号始终按正常时间顺序，不能倒置内容或上传顺序。会员模式忽略此分段选择。
- `telegram_api_id`、`telegram_api_hash`：Telegram 应用凭据，扫码仍需提供。
- `telegram_proxy`：Telegram 代理，支持 socks5/socks4/http。
- `http_proxy`：仅 JAVHD 页面和媒体下载代理。
- `javhd_cookies_file`：用户自己的 Netscape Cookie 文件；相对路径以 skill 根目录为基准。解析使用页面内部 ID，以 `is_trailer=0` 查询完整源；接口拒绝访问、无源或仅返回预告片时失败，不退回预告片冒充完整视频。
- `upload_concurrency`：默认 6，范围 1–16；实际在途分块上限 10。
- `notify_saved_messages`：默认 true，另向 Telegram“收藏夹”发送 ID/状态通知，不向频道额外发布通知。

支持环境覆盖：`TG_API_ID`、`TG_API_HASH`、`TG_PROXY`、`HTTP_PROXY_URL`、`JAVHD_COOKIES_FILE`。**频道 ID 不从环境变量读取**，只能更改本地配置。

夸克上传调用内置的官方 CLI 1.0.20（`vendor/quarkclouddrive/scripts/quark-drive.cjs`），固定以 Claude Code 宿主标识（`CLAUDECODE=1`）启动，新任务生成会话 ID，续传复用清单中的原会话。启动前校验两个 vendor 文件的 SHA-256 并要求 Node.js 16+。vendor 内容和校验值保持不变；项目自有的 `scripts/quark_proxy.cjs` 复制到 `.state/quark-cli/scripts`，通过 Node `--require` 预加载，接管 SDK 显式创建的 HTTP/HTTPS Agent，并通过专用临时控制文件触发官方中止保存处理。不执行官方安装脚本或自动升级。

### 夸克代理路由（仅作用于夸克子进程）

按 `QUARK_PROXY` → `HTTPS_PROXY` → `ALL_PROXY` → `HTTP_PROXY` 的顺序选择第一个非空变量，支持对应小写名，同名大写优先。只支持 HTTP/HTTPS 代理 URL，认证信息从环境读取且必须正确 URL 编码；不支持的协议、错误格式直接报代理配置失败，不猜测或回退。禁止把真实代理地址、凭据或会话加入代码、配置示例、命令行、日志或分发包。

选择代理后，账号查询、OAuth 请求、目录操作、上传端点和合并请求全程使用同一条代理；不根据 `NO_PROXY` 让某些域名直连。未配置则直连，`QUARK_PROXY=direct` 可显式强制夸克直连。只在 CLI 子进程里传递代理，父进程环境不变，Telegram 逻辑和其代理配置不变。网盘目标仍从根目录 `0` 定位/创建 `JAVHD`，不因代理切换改变。

HTTPS 目标经 CONNECT 隧道；代理 URL 的协议表示代理监听协议，而不是目的站协议。普通 HTTP CONNECT 代理不能误配成 HTTPS 代理，否则可能得到 `EPROTO` / `SSL wrong version number`。代理自身和目的站 TLS 都验证证书；企业 CA 可由环境 `NODE_EXTRA_CA_CERTS` 提供，不关闭证书校验。浏览器授权页仍使用浏览器自身网络，不由 Node 适配器设置系统代理。

### 两种环境分别自检

- `<PYTHON> -I <SKILL_ROOT>/scripts/main.py --check`：本地文件、SHA-256、Node 和代理配置检查，不联网；返回 `quark_network_mode`、`quark_proxy_source`，不回显代理值。
- `<PYTHON> -I <SKILL_ROOT>/tests/quark_network_check.py --direct`：只对此次夸克自检强制直连。
- `<PYTHON> -I <SKILL_ROOT>/tests/quark_network_check.py --require-proxy`：必须从环境取到可用的代理配置，没配置就失败，不直连兜底。

后两项只探测官方 API 的 TLS/HTTP 可达性，不加载官方 CLI、不读授权、不创建目录或上传文件。HTTP 响应不代表业务成功；成功还会返回 `tls_verified=true`、`authorization_checked=false`，业务授权和非秒传上传须另验。**本地直连通过不等于 Muse VM 等代理环境通过**，必须在目标 VM 单独验证代理链路。

适配器把直连故障、代理故障、明确的 OAuth 未授权分别归类。`write EPROTO` 等网络错误优先判定为对应链路失败，不能包装成“授权未完成”或索要授权码。只有浏览器等待/打开失败才提供本地授权码补充入口。超时或上传未确认不自动整项重传。

官方 CLI 使用 OAuth/刷新令牌，与旧 quarkpan 的网页 Cookie 是两套体系。旧 `.state/quark` Cookie 不能给新 CLI 使用，也不能用复制 Cookie、会话或 API 密钥的方式修复代理问题。此路由不读取 `config.json` 中的 `http_proxy` 或 `telegram_proxy`。

## 事件与退出码

标准输出通常是 UTF-8 JSON Lines，每行一个事件。无效原始输入例外：只输出格式提示，退出码为 2。依赖库可能向标准错误输出诊断信息；不能把标准错误中的文本当最终结果。

主要事件：

| `event` | 含义 |
| --- | --- |
| `check` | 依赖及配置就绪状态 |
| `qr` | Telegram 新二维码，字段为 `service` 和 PNG 的绝对 `path` |
| `login` | 某侧状态更新，字段为 `service`、`status` |
| `login_result` | 本次指定登录目标的最终状态及安全错误信息 |
| `stage` | 视频任务阶段：`download` 或 `upload` |
| `transfer` | 单个文件上传的统计：字节数、耗时、KiB/s、并发数、平均确认延迟 |
| `telegram_split` | 电报已准备分段；含段数、原视频字节数、单段兼容上限和 `direction`，不含标题或文件名 |
| `result` | 视频任务的最终结果；以本次进程的这一事件为准 |
| `batch_result` | 批次最终汇总，含按输入顺序的 `results`、`success_count`、`failed_count`、`skipped_count` 和 `interrupted` |
| `cleanup_result` | 用户选择删除后的结果；`cleaned=true` 才能确认已删除 |
| `stopping` | 中止请求已收到，正在等已启动的任务结束，再按实际结果清理或保留 |
| `error` / `close_error` | 启动/退出错误，不表示媒体已上传成功 |

退出码：`0` 为命令成功，批量时必须所有项成功；`1` 为运行/配置/上传失败（批量任一项失败）；`2` 为输入或 CLI 参数错误；`130` 为中止，批量完成保留收尾后也返回此码。`--check` 的 0 仅表示本地自检完成，还必须检查各项 `*_ready`，不代表已登录或有发布权限。

最终成功结果的必要字段示例：

```json
{
  "event": "result",
  "id": "123",
  "telegram": "success",
  "quark": "success",
  "cleaned": true,
  "retained": false,
  "awaiting_decision": false,
  "db_recorded": true,
  "record_id": "9007199254740993",
  "saved_message": true,
  "notification": "id:123 上传成功"
}
```

此示例省略了可选的远端 ID 和错误字段。`saved_message=false` 只表示“收藏夹”通知未发送或已禁用，不会把已成功的上传改成失败；聊天仍需通知。反之，`saved_message=true` 也不代表上传成功，应检查两侧状态。

上传业务记录使用 Cloudflare D1 REST API，配置和 11 个字段见 [D1 说明](d1.md)。`record_id` 为雪花主键，`db_recorded=true` 表示当前元数据及两端状态/远端 ID 已确认写入，仍须分别判断上传状态。各平台分别更新自己的列；D1 故障保留真实上传结果并提示“D1记录未确认”，不写文件兜底。两端成功而 D1 未确认时保留任务，`--retry` 只补写数据库。

## 登录与任务生命周期

运行时目录：

```text
.state/
  qr/telegram.png
  login-telegram.json
  login-quark.json
  telegram.session
  quark-cli/              官方 CLI 运行副本及本机授权
  task.lock
```

夸克授权不在这里：官方 CLI 把授权保存在其运行目录的上两级，即 `.state/quark-cli`，不进入 `vendor/`，也不打包。

登录状态包括 `connecting`、`scan`、`ready` 和 `failed`。错误处理可能将中间状态更新为 `failed`，应结合本次 `login_result.errors` 判断原因。

- 首次两侧登录同时发起；已有有效会话时不会重复授权。夸克只在只读账号查询明确返回未授权时启动浏览器授权。
- Telegram 的 `qr` 事件表示已经生成新的 PNG；优先按事件展示，使用文件等待时必须核对本次修改时间和 `scan` 状态。
- Telegram 大约每 30 秒刷新二维码；成功后删除对应 PNG，保留会话。夸克浏览器授权失败或超时后，只由本地用户把授权码粘贴回终端，一次性交给官方 CLI，不再重复自动启动授权。
- `电报重登` 退出本工具旧的 Telegram 会话；`夸克重登` 不主动撤销官方授权，只在本机授权无效时重新完成浏览器授权，不影响其他客户端登录。
- 必须在执行进程所在机器保存并展示 QR 文件；agent 仅能读文字时，应让用户在该机器上打开图片。
- 进程不存活，扫码或授权就不能完成。宿主不能持续运行进程时，转为本地终端操作。

## 完整性、清理与不确定结果

目前仅处理普通完整 MP4；HLS、无中文标题、仅预告片或完整源接口拒绝访问会失败。下载长度和容器检查用于确认文件下载完整；页面标注时长仅作参考，不用它否决完整源，也不能单凭文件时长证明内容一定完整。

动态预览可能原本就是短 MP4，也可能是 GIF；没有当前视频自己的预览时从同一视频生成。工作室详情页的公开 ID、播放器内部 `videoId` 和预告媒体目录 ID 可能不同；没有显式预览字段时，用当前页已验证的播放器 endpoint 保留内部 ID/路由/其他参数，设 `is_trailer=1`，只从该响应的 `trailers/<媒体ID>/...mp4` 提取目录。优先核验同目录五秒预览，再核验接口实际提供的预告 MP4，每个候选最多读取 64 字节并检查 HTTP 状态和 MP4 文件头。工作室不按公开或内部 ID 猜媒体目录，不从推荐卡片取预览，完整源不能因预告模式被忽略而当作预览；预览失败不清空完整源。普通页面保留公开 ID 五秒预览路径，不可用时同样可查当前播放器预告。实际 Telegram 相册中预览是无声 MP4，不是原生 GIF 动画。中文文件名仅替换非法字符并限制过长名称，标签不进入夸克文件名。Telegram 说明固定带上 `#ID{视频ID}`（例如 `#ID123`，使用大写 `ID`，未填标签时仅此一项），纯数字标签如 `#123` 自动转为 `#ID123`，其他标签按原文保留；按顺序去重，并按实际标签长度设置 `MessageEntityHashtag` 实体。

只有两侧上传及 D1 保存都确认成功才自动删除本次任务。任何上传、数据库失败、未确认或取消后的文件均保留，返回 retained_dir 和 awaiting_decision，等待用户决定；登录态和 D1 云端记录不属于媒体清理范围。中止时等已启动的上传结束，不在同步线程读文件时清理。

电报按 `telegram_premium` 选择模式：`false` 时采用 4000 × 512 KiB（约 2GB）的普通账号兼容上限，超过后由 `scripts/telegram_media.py` 流式分析视频关键帧和音视频包大小，预留容器开销，使用 FFmpeg 无重新编码分段并检查实际大小；`true` 时完全跳过切割，以 8000 × 512 KiB（约 4GB）的会员兼容上限上传原视频，超限明确失败。`--check` 返回本次 `telegram_premium` 和 `telegram_video_limit_bytes`。普通账号的分段文件在原视频所在任务目录的新 `telegram-parts-*` 目录中，按 `中文标题(1).mp4` 等连续编号；每段可独立播放且保留音频，采用各段自己的时长信息。主任务设置 `retain_work_files`，由它统一决定清理；失败时分段与原视频一起保留，只有双端成功或用户选择删除才清理。

普通账号的 `telegram_split_direction=head` 从开头按字节预算选切点，最后一段放余量；`tail` 保存关键帧的累计音视频包字节位置，从总字节数向前尽量填满后面的段，将余量留在首段，再把切点按时间升序交给 FFmpeg。两者都保留关键帧对齐、实际体积验证及缩小预算重试，文件和相册仍按 `(1)`、`(2)` 的正常播放顺序发送。`--check` 也返回本次 `telegram_split_direction`；分段事件 `direction` 表示实际使用的规划方向。

电报仅发送一次动态预览，随后按段号顺序发送所有视频段；每批相册含 2–10 个条目。每批均核对本次 random_id 和 grouped_id，全部批次确认后才返回成功及有序消息 ID。部分相册已发布而后续失败时，电报仍报告失败，必须先查频道，不能自动整项重发；不影响夸克继续上传原视频。`telegram_split` 仅表示本地分段完成，不证明发布成功。无法在关键帧边界生成上限内的独立视频时明确失败，不上传超限文件或用二进制碎片冒充 MP4。

夸克侧只把官方 CLI 的最终结果 `code=0` 且返回文件 ID 视为成功；官方命令单次超时 30 分钟。超时、中断、无文件 ID 或本地文件在过程中变化时报告“未确认”，不自动重传，应先检查网盘。旧实现的 `.state/quark` Cookie 已不再使用，也不会被自动导入官方授权。

固定版 CLI `1.0.20-5be3987` 已通过离线帮助核对，提供 `upload list` 和 `upload resume --record-id`，后者支持 `--file-path` 重新关联原文件。主流程通过 `Quark.upload_resumable` 保存 `quark_upload`：首次上传前写入 `attempted=true`、文件名/大小/mtime、原会话、目标 FID、同名同大小的已有记录 ID 和开始时间；官方 list 行的 `recordId` 无论成功或失败都立即保存。清单保存与电报结果更新共用线程锁，避免并发覆盖。

`--retry` 对已开始的夸克任务只使用 `upload resume --record-id <ID> --file-path <原文件>`。缺少直接返回的 ID 时，查询持久化记录，只关联同名同大小、创建时间在本次上传期间、且不在已有记录中的唯一新任务；无匹配或多匹配均拒绝。恢复前再次校验文件和断点；记录不存在、已过期、状态异常、旧版清单缺少续传信息时停止，不退回全量上传。记录显示 `success` 但未保存原成功结果时需先核查网盘。新格式 `attempted=false` 的任务可正常开始首次上传。

续传的 result 不带 `fids`；必须同时收到同一 `recordId` 的成功 list（匹配文件名、大小及非空 `fileId`）、最终 result `code=0` 和进程退出码 0 才算成功。进度和单独的任务 ID 不算成功。超时或 CLI 中止先经预加载器触发官方 SIGINT 保存处理，最多等 8 秒后强制终止；结果仍报告未确认，不能保证强杀/断电一定有有效断点。底层 `upload_file` 保留单次新上传接口供手动测试使用，不用它替代保留任务的续传。

保留目录中的 `upload-task.json` 保存相对路径、媒体指纹、必要元数据、D1 记录 ID、用户指定详情页 URL、原任务频道和已成功端的远端 ID；不含 API Token、Cookie、授权或临时视频下载链接。每端成功后更新清单，任务收尾再记为 `retained` 或 `complete`。`--retry` 校验目录范围、任务状态、文件指纹和频道一致性；已有完整媒体时不下载，不重新登录或上传已成功端。若上次进程中断而清单仍为 `running`，应先核查远端，不能直接重试。未完成预处理的任务在目录内使用原详情页重新准备媒体，不复用临时链接。

`--retry` 与 `--delete` 不能混用普通视频、登录或自检参数，且共用 `.state/task.lock`。删除前重新解析目标，必须是当前 skill 的 `downloads` 下一个真实的直接子目录；拒绝根目录、符号链接、目录联接及越界路径。显式删除不读取账号配置，不影响其他任务、会话和 D1 记录。操作失败不假报成功；部分删除后的残留需核对。删除不会修改 D1 上传行。

同一个 ID 通过新 `--id` 再次执行仍会重新发布，不会按 D1 既有成功状态自动跳过，新任务更新该视频最新结果。跨进程恢复应使用原保留任务的 `--retry`，同时保留原 `.state/` 官方持久化记录。失败后不自动重试整项任务；电报部分发布或清单为 `running` 时先核查远端。被运行锁拒绝的调用，不得使用其他进程或旧文件的成功结果。
